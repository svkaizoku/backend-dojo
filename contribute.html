Ways to help

Add an exercise

Turn a bug you've seen in a real code review into a short pull request with an answer key.

Improve an answer key

A wrong line, an unclear explanation, or a missing keyword that made Quick check miss a good review.

Report a problem

Something broken or confusing? Open an issue with the exercise name and what you expected.

Improve the app

Plain HTML, CSS and JavaScript modules in js/ and css/. Edit, reload, done.

Add an exercise

An exercise is one folder: the code under review in Java, Kotlin or both, plus an exercise.json answer key.

  1. Fork and run it locally

    Fork the repo on GitHub, clone your fork, and serve the folder. Any static server works.

    git clone https://github.com/<you>/backend-dojo.git
cd backend-dojo
python3 -m http.server 8000

  2. Create a folder

    Use a short, lowercase id with dashes. It becomes the link to the exercise.

    content/exercises/settlement-batch/
  exercise.json
  SettlementJob.java
  SettlementJob.kt

  3. Write the code under review

    About 20–40 lines that look like a real pull request: realistic names, no imports, no comments pointing at the bugs. Write the Kotlin version idiomatically, not as a line-by-line translation.

  4. Write the answer key

    Describe each planted issue in exercise.json (format below). Point each one at its line with a piece of text from that line.

  5. Register it

    Add the folder name to "exercises" in content/index.json.

  6. Validate and preview

    The validator checks the format and that every issue points at exactly one line. Then open the exercise and try both Quick check and the answer key.

    node scripts/validate.mjs
open http://localhost:8000/practice.html#settlement-batch

  7. Open a pull request

    CI runs the same validator. Say in the description what the exercise teaches and where the pattern comes from.

File format

exercise.json
{
  "title": "Settlement batch",
  "topic": "data",
  "level": "Standard",
  "context": "Nightly job that settles trades. Runs on
              two instances behind a scheduler.",
  "files": { "java": "SettlementJob.java",
             "kotlin": "SettlementJob.kt" },
  "refs": [
    { "title": "Further reading", "url": "https://…" }
  ],
  "issues": [{
    "sev": "major",
    "title": "Job runs twice in parallel",
    "at": { "java": "@Scheduled(cron",
            "kotlin": "@Scheduled(cron" },
    "why": "Both instances run it, so trades settle twice.",
    "fix": "Use a scheduler lock such as ShedLock.",
    "kw": ["shedlock", "both instances", "twice"]
  }]
}
FieldWhat it is
titleShort name shown in the exercise list.
topicOne of the topic ids below.
levelWarm-up, Standard or Hard.
contextThe PR description. Include every fact a reviewer needs, such as "singleton" or "runs on several instances".
filesCode file per language: java, kotlin or both.
refsOptional further reading, shown under the answer key. https links only.
sevmajor (must fix) or minor (should fix). Major counts double in the score.
atText from the issue's line, per language. It must match exactly one line. Leave a language out if the issue only exists in the other.
title, why, fixOne string, or { "java": …, "kotlin": … } when the wording differs.
kwLowercase phrases for Quick check. A review containing any of them counts as found.

What makes a good exercise

Realistic

Code a teammate could plausibly open a PR with. The bugs should come from real reviews, not puzzles.

Findable

Every issue can be spotted from the code and the PR description alone. State the facts that matter, such as threads, instances or data sizes.

Focused

4–8 issues, mostly must-fix, with a few should-fix. Skip pure style nits that a linter would catch.

Explained

why describes the impact in production, and fix is concrete enough to act on.

Fair to Quick check

Keywords are specific phrases a good review would use, like "computeifabsent", not words like "bug" that match anything.

Correct

Check claims about library behaviour by running code when you can. A wrong answer key teaches the wrong thing.

Licensing and sources

Your contribution is CC BY 4.0

Exercises are shared under CC BY 4.0 and app code under MIT. By opening a pull request you agree to license your work that way.

Write it yourself

Bug ideas and patterns are free to reuse. Code and text copied from books, courses or blogs usually aren't, even if they're public.

Link, don't copy

Point to the article or docs that explain a pattern well in refs.

Open sources are fine

Material under MIT, Apache 2.0 or CC0 can be adapted. Credit it in refs.

Pull request checklist

  • node scripts/validate.mjs passes.
  • The exercise opens on the practice page, in every language it has.
  • Show answer key pins each issue on the right line.
  • A good review gets a high score with Quick check.
  • The code and text are your own, or come from an openly licensed source credited in refs.
  • The folder is listed in content/index.json.
